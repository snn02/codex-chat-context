## Итог

Оба первоначально запрошенных факта подтверждены в Codex 26.1007.71326 (build 20398): собственный интерфейс плагина открывается справа одновременно с перепиской; настоящий ID текущего чата автоматически передаётся серверу в метаданных MCP и доступен интерфейсу через результат инструмента. Дополнительный тест переключения также подтвердил правильные ID в проверенных вызовах двух чатов и после возврата. Панель скрывается при уходе из своего чата и восстанавливается при возвращении; во втором чате открыт отдельный экземпляр. Подробные доказательства и границы проверки ниже.

## Проверка присланного скриншота — до нового чата

Пользователь прислал карточку `List MCP resources once` с ошибкой `unknown MCP server 'context_panel_probe'`. Это результат диагностического tool call в переписке, не HTML-интерфейс плагина. В журнале по-прежнему нет ни `open_panel`, ни `report_binding`. Единственный `resources/read` относится к ручному smoke test. Следовательно, считать панель открытой нельзя.

Причина отсутствия сервера именно в инструментальном окружении текущего чата не установлена. Его наличие в отдельном app-server не доказывает наличие в этом окружении. Предположение о том, что повторное @-упоминание обновит инструменты, экспериментально не подтвердилось. Следующий отдельный тест — новый чат с плагином, установленным до старта; создавать такой чат следует только по явному запросу пользователя. Успех этого теста не гарантирован.

Текущая сборка формирует hostContext с темой, режимом отображения, размерами и toolInfo; явного threadId в исследованной функции нет. Поэтому получение ID надо проверять фактическим вызовом, а не предполагать.

## Предыдущий следующий шаг — до нового чата

Упоминание через @ не добавило сервер в доступный набор инструментов текущего агентского сеанса: `list_mcp_resources` ответил `unknown MCP server`. Повторять упоминание больше не нужно.

Открыть меню текущего чата → Plugins / Плагины → Context binding probe (или Context Panel Probe). Затем проверить resources/read и report_binding в probe-events.jsonl. Это позволяет проверить UI независимо от каталога инструментов модели.

Признаки успешной проверки: UI успешно выполнил ui/initialize; хост вызвал report_binding; установлено, откуда получен ID; этот ID совпадает с чатом. Затем повторить в другом существующем чате, если пользователь разрешит такую проверку.

## Интерпретация данных

- `identity`: разрешённые служебные поля из метаданных фактического MCP-запроса.
- `processThreadId`: переменная окружения процесса; сама по себе НЕ доказывает привязку к открытому чату.
- `report`: служебные данные, полученные UI при инициализации в хосте.
- `instance`: случайный ID экземпляра UI, НЕ ID чата.
- Первый initialize в журнале создан ручным smoke test, а не открытием панели.
- Поздние initialize и tools/list также могут относиться к отдельному `diagnose-probe.cjs`; только `report_binding` после инициализации UI подтверждает работу bridge. Вызов resources/read из smoke test сам по себе не подтверждает UI.

Плагин не читает журнал переписки, не использует сетевые запросы и не передаёт данные внешним сервисам. Его единственная запись — локальный probe-events.jsonl с диагностическими полями.
